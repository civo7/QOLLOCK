## 1. Executive Summary

QoL Lock is a 31,408-line Deadlock Panorama HUD mod that injects ~80 configurable
features into the game's UI. It is *the* most sophisticated Deadlock mod in
existence — its engineering quality (scheduler, gate system, schema versioning,
perf infrastructure, idle degradation) exceeds every other mod in the ecosystem
by a wide margin.

**Key numbers:**
- **31,408 lines** in `ql_core.js` (the main runtime)
- **3,794 lines** in `ql_shared_presets.js` (defaults, codec, presets)
- **614 lines** in `ql_utils.js` (shared utilities, extracted via Fix 10)
- **~33,000 lines** in `ql_settings.js` (settings UI — too large to read fully)
- **~80 configurable features** with ~170 config keys
- **~600 State fields** tracking runtime state
- **5-phase bucketed scheduler** dispatching ~40 feature groups across 8 offset buckets per tick
- **Schema version 3.1.4** with compact binary encoding for export/import
- **25 presets** contributed by community members

The mod is GPU-stable (FPS impact is negligible when features are off) but has
several CPU-efficiency opportunities, resilience gaps, and code-health concerns
at its current scale.

## 2. Architecture Overview

### 2.1 File Roles

| File | Lines | Role |
|------|-------|------|
| `panorama/scripts/ql_utils.js` | 614 | Shared utility library — panel validation, safe attribute I/O, perf timing, logging, angle math |
| `panorama/scripts/ql_shared_presets.js` | 3,794 | Source of truth — QOL_DEFAULT_CONFIG, QOL_CODEC, QOL_SCHEMA_UTILS, QOL_PRESETS, all normalization functions |
| `panorama/scripts/ql_core.js` | 31,408 | Main runtime — the core polling loop, all feature implementations, build category payload system, account preset binding, settings loaders |
| `panorama/scripts/ql_settings.js` | ~33,000 | Settings UI — tabbed menu, row creation, compact schema registry, config read/write, export/import |
| `panorama/styles/hud_health.css` | — | Health bar CSS for all 6 healthbar modes |
| `panorama/layout/hud_health.xml` | — | Health container layout injection |

### 2.2 Three-Loop Architecture

QoL Lock runs **three independent polling loops**, each with its own degradation:

| Loop | Base Interval | Degradation | Purpose |
|------|--------------|-------------|---------|
| **Main/Core** | 200ms (5 Hz) | 0.5s idle / 1.5s deep-idle / 3.0s background | All HUD features, config monitoring, perf flushing |
| **Compass** | 50ms (20 Hz) | 0.5s idle / 1.0s deep-idle | Compass rotation, minimap rotation, item mirror CD rings, reload CD, ult CD, target shapes |
| **Build Request** | 50ms–1.80s (active/idle/deep-idle) | Game-state-aware | Build category payload save/clear orchestration, hero switching |

### 2.3 Dependency Loading Order

```
hud.xml loads scripts in this order:
  1. ql_utils.js          (shared utilities)
  2. ql_shared_presets.js (defaults, codec, schema utilities)
  3. ql_core.js           (main runtime — checks QOL_UTILS_LOADED)
  4. ql_settings.js       (settings UI)
```

`ql_core.js` gracefully degrades if `ql_utils.js` isn't loaded (for schema validator
sandbox compatibility), with inline stubs for every utility function.

## 3. Core Loop & Scheduler Deep Dive

### 3.1 The `loop()` Function (line ~30798)

The main loop is an `$.Schedule`-based recursive callback with this structure:

```
loop():
  1. Read raw config from panel attribute storage (cached if unchanged)
  2. Parse config (JSON → object) or reuse cached config
  3. Apply forced feature disables
  4. Update perf tracking state from config
  5. Compute next scheduler phase (0–4, cycling)
  6. Process pending hero restore if any
  7. Apply build category payload override if active
  8. Detect hideout connection state
  9. HARD-GATE: if all features are disabled and nothing pending, skip everything
  10. Sweep stale cached panels once per second
  11. ResolveRuntimeGates() — compute which features need to run this tick
  12. Collect features into 8 offset buckets (0ms, 17ms, 33ms, 50ms, 67ms, 83ms, 100ms, 117ms)
  13. Dispatch buckets via $.Schedule at staggered offsets
  14. Update settings loader overlays if active
  15. Flush perf stats if due
  16. Record frame time for low-FPS detection
  17. Compute next interval via GetDynamicLoopInterval() based on idle state
  18. $.Schedule(nextDelaySec, loop)
```

### 3.2 The 5-Phase Core Scheduler

The `CORE_SCHEDULER_V2_ENABLED` system (line ~805) spreads heavy features across
5 consecutive ticks to avoid CPU spikes:

| Phase | Slot | Features Assigned |
|-------|------|-------------------|
| 0 | `CORE_PHASE_REJUV_NICKNAMES` | Rejuv/buff timers, nicknames, core root classes |
| 1 | `CORE_PHASE_SPM_STATLOCKER` | SPM (souls per minute), statlocker |
| 2 | `CORE_PHASE_UNSPENT_LANE` | Unspent souls, lane-with-party |
| 3 | `CORE_PHASE_UNSECURED` | Unsecured souls overlay |
| 4 | `CORE_PHASE_STAT_BONUSES` | Stat bonuses overlay |

This means heavy features like SPM panel scanning don't overlap with unspent
soul tier scanning in the same tick — each gets its own 1-second window before
repeating.

There's also a **staggered cleanup** system (`CORE_SCHEDULER_STAGGER_CLEANUP`):
when a feature is disabled, its disable-cleanup code is spread across 3 phases
instead of running all at once.

### 3.3 Intra-Tick Feature Bucketing

Within each tick, features are dispatched at 8 staggered offsets:

| Bucket | Offset | Features |
|--------|--------|----------|
| 0 | 0ms | rejuvTimers, coreRoot |
| 1 | 17ms | spm, nicknames, healthbarRuntimeHelpers |
| 2 | 33ms | unspent, statlocker, signatureFlash |
| 3 | 50ms | bottomBarRuntime, itemsRuntime, soulsRuntime |
| 4 | 67ms | ammo, topBarRuntime, heroShop |
| 5 | 83ms | colorWarning, enemyColorWarning, allyColorWarning, targetShapes, damageNumbers |
| 6 | 100ms | keyboardRuntime, zipBoost, unsecuredSouls, statBonuses |
| 7 | 117ms | panelCache, onDeathArcade, laneWithParty, gameplayMouseCursor, betterUnsecuredHud, combatStatus, damageImpactRuntime, staminaChargeColorRuntime, minimapRuntime, legacyAudioPassive, imagesInChat, recentPurchases, healthbar accent color sync |

**Rationale:** At 60fps (~16.7ms/frame), the 200ms loop fires every ~12 frames.
By staggering features across 7 offset buckets within those 12 frames, the CPU
load is spread evenly instead of spiking at t=0. The 0ms bucket handles the
most latency-sensitive features; the 117ms bucket absorbs the least critical.

When `FEATURE_STAGGER_ENABLED = false` (rollback switch), all features execute
synchronously from bucket 0 — useful for debugging.

### 3.4 Idle Degradation System (Fix 9)

The `DetectGlobalIdleState()` function (line ~11423) determines a 4-level
degradation state:

| Level | Condition | Main Loop Interval | Effect |
|-------|-----------|-------------------|--------|
| `active` | In match, HUD visible, FPS > ~20 | 200ms (5 Hz) | Full speed |
| `idle` | HUD hidden or FPS < ~20 | 500ms (2 Hz) | 2.5× slower |
| `deep_idle` | Not in match | 1.5s (0.67 Hz) | 7.5× slower |
| `background` | Extended deep idle | 3.0s (0.33 Hz) | 15× slower |

Detection is cached for 2 seconds (`IDLE_DETECTION_CACHE_MS = 2000`) to avoid
per-tick overhead. The low-FPS path requires perf tracking to be enabled
(`ENABLE_PERF_DEBUG`).

**Current limitation:** The hard-gate optimization (`State.allFeaturesDisabled`)
is a boolean — when true the loop enters a fast-path that skips all gate
computation and feature execution entirely. This is excellent when all features
are off. However, when even a single feature is on, the loop must evaluate all
~40 gate conditions every tick even though only one feature actually runs.

### 3.5 The Gate System

`ResolveRuntimeGates()` (line ~30342) computes a boolean gate for every feature
group. Gates are cached and only recomputed when config changes (detected via
signature comparison). Key design decisions:

- **Sticky-state cleanup:** When a feature is disabled, its gate stays true for
  a few ticks (`ShouldRunStaggeredDisableCleanup`) so the runtime can undo CSS
  classes, reset panel styles, and clear caches.
- **Feature-state precomputation:** `BuildRuntimeFeatureConfigState()` computes
  derived boolean flags once per config change, avoiding repeated `IsCfgEnabled()`
  calls across ~40 gate checks.
- **Compass-loop gates:** Pre-computed once per main-loop tick (5 Hz) and read
  by the compass loop (20 Hz), saving 11+ repeated config reads.
- **Hard-gate optimization:** `State.allFeaturesDisabled` lets the loop skip
  gate computation entirely when nothing is active.

### 3.6 Feature Error Isolation (Fix 6)

The `ExecuteFeature()` wrapper (line ~3363) provides per-feature error isolation:

```
ExecuteFeature(name, fn):
  if feature auto-disabled → skip
  try:
    fn()
    reset error streak
  catch:
    log throttled error
    increment error streak
    if streak ≥ FEATURE_ERROR_STREAK_MAX → auto-disable feature
```

This prevents one crashing feature from corrupting State for all other features
in the same tick. Auto-disabled features stay disabled for the session.

## 5. Config & Schema System

### 5.1 Config Storage

Config is stored as a JSON string under panel attribute `"Deadlock_Mod_Settings_v1"`
on up to three panels: the context panel, the root panel, and the `Hud` panel.
A separate `"QOL_USER_EDIT_REV"` attribute tracks revision numbers.

On read: the entry with highest revision wins (priority: hud > root > panel for ties).
On write: all three targets are updated simultaneously with incrementing revision.

### 5.2 Schema Versioning

- **Current semver:** `3.1.4` (defined in `ql_shared_presets.js`)
- **Wire version:** `2` (for compact binary encoding)
- **Encoding:** Compact binary — each field is bit-packed based on its `(max - min) / step` slot count
- **Format:** `[QOL-3-1-4]:<base64url(binary_data)>`
- **Checksum:** Simple 8-bit sum appended to binary payload

The schema uses a registry pattern in both `ql_settings.js` and `ql_core.js`:
```js
SCHEMA_REGISTRY = {
  "3.1.3": { fields: [...], wireVersion: 1 },
  "3.1.4": { fields: [...], wireVersion: 2 }
}
```

`ResolveSemverFromWire()` maps wire versions back to semvers for decoding.

### 5.3 Normalization Pipeline

When config is loaded, a cascade of normalization functions runs:
1. `NormalizeHealthbarTypeConfig()` — legacy boolean keys → HEALTHBAR_TYPE enum
2. `NormalizeColorWarningConfig()` — legacy boolean → per-threshold keys
3. `NormalizeEnemyColorWarningConfig()`
4. `NormalizeAllyColorWarningConfig()`
5. `NormalizeTopbarEnemyHpWarningConfig()`
6. `NormalizeTopbarAllyHpWarningConfig()`
7. `NormalizeNeutralCampTierConfig()` — legacy tier → per-tier keys
8. `NormalizeAmmoScaleConfig()` — legacy AMMO_PANEL_SCALE → AMMO_CURRENT/TOTAL
9. `NormalizeItemCooldownModeConfig()` — legacy OLD_ITEM_COOLDOWNS → PASSIVE_COOLDOWN
10. `NormalizeVoiceTypeConfig()` — legacy beep index → new voice type
11. `NormalizeShopItemNotificationsConfig()`
12. `NormalizeCompassSpeedSchemaMigration()`
13. `NormalizeLanguageSchemaMigration()`
14. `MigrateSplitZoomKeys()` — legacy ZOOM → split alt/tab zoom keys

This is a sophisticated system but represents significant accumulated tech debt —
every new setting that changes semantics requires a new normalization function
and careful ordering.

### 5.4 Build Category Payload System

Settings can also be persisted into Deadlock's hero build system (using
`hero_airheart` as the storage slot). This is a multi-step state machine that:
1. Switches the hero selection to `hero_airheart`
2. Opens the shop
3. Navigates to the build category
4. Reads/writes the build name as a compact binary payload
5. Switches back to the original hero

The system handles corruption repair, retry logic, bootstrap from default,
save/clear request queues, session management, and ESC-closed prompt recovery.
This is the most complex subsystem in the mod (~500 State fields for this alone).

### 5.5 Account Preset Binding

At startup, the mod probes panel attributes to discover the local account ID,
then checks a hardcoded binding map to auto-apply a named preset. The binding
only applies at bootstrap — users can change settings after.

## 6. Performance Infrastructure

### 6.1 Perf Tracking System

Controlled by `ENABLE_PERF_DEBUG` and `ENABLE_PERF_DEBUG_DETAIL` config keys:

- **PerfStart()/PerfEnd():** Paired timing calls around every feature execution
- **PerfRecord(name, ms):** Accumulates count/total/max/slow stats per named measurement
- **FlushPerfIfNeeded():** Periodically dumps top-N stats to console (sorted by total time)
- **Perf overlay:** Separate `QOL_PERF_OVERLAY` module renders live stats on screen
- **Module-level cache:** `_perfTrackingActive` boolean avoids 70+ property lookups when off

Output format:
```
[QOLLock][Perf] window=30000ms loopHz=5.0 compassHz=20.0
  top=loop.souls_per_min=avg:0.45ms,max:2.1ms,n:150,slow:2 | ...
```

### 6.2 Profiler (ql_utils.js)

A separate call-count profiler tracks function call frequency:
- **ProfileHit(name):** Increments per-function counter (enabled via `SetProfilerEnabled`)
- **DumpProfile():** Periodically prints top-15 most-called functions
- **Rolling window:** 60s, dumping every 10s

### 6.3 Frame Timing (ql_utils.js)

Frame budget tracker measures per-tick elapsed time:
- **TimeFeature(name, startMs):** Records feature duration
- **RecordFrameTime(elapsedMs):** Records overall tick timing
- **DumpTiming():** Prints frame budget summary with >50ms/ >100ms spike warnings
- **Rolling window:** 60s, dumping every 10s

### 6.4 Logging System (ql_utils.js)

Four log levels with per-category throttling:
- `DebugLog(cat, msg)` — only when `DEBUG_ENABLED = true`
- `InfoLog(cat, msg)` — significant state changes, throttled
- `WarnLog(cat, msg)` — unexpected but recoverable, throttled
- `ErrorLog(cat, msg)` — actual errors, throttled

Default throttle: 2000ms per category. Debug toggle: `ToggleQollockDebug()` in console.

## 7. Findings & Issues

### 7.1 Critical — Resilience

**F1. Empty config parse catch.** `ReadStorageConfigRawFromUi()` uses an empty
`catch(e) {}` when JSON parsing fails. A corrupt config string causes parse
failure on every tick (5/sec × 3600 = 18,000 failures/hour) with no logging
and no auto-recovery. (Identified as Fix 7 in stability proposals.)

**Status:** Unresolved. The codec now has checksum validation for compact
binary, but the outer JSON parse still silently swallows errors.

**F2. Stale panel references.** 23+ unsafe cached panel access sites identified.
While `ql_utils.js` now provides `IsPanelValid()`, `GetCachedPanel()`,
`SetCachedPanel()`, `SweepStalePanelCache()`, and `ResolveCachedPanel()`, the
adoption is incomplete — many features still access `State.cachedPanels[key]`
directly without validation. (Identified as Fix 1.)

**Status:** Partially resolved. The infrastructure exists but hasn't been
retrofitted to all cache access sites. The 1Hz sweep catches stale refs but
leaves a window for accessing destroyed panels between sweeps.

**F3. XML override fragility.** QOLLOCK ships 28 modified copies of Valve's
original XML layout files. When Valve updates the game, these copies silently
drift out of sync — panels change IDs, new required attributes appear, or
hierarchies shift. This is the #1 source of game-update breakage.

**Scope:** 28 XML files, every one a full copy of Valve's original with
modifications. Here is every file, what was changed, and what breaks:

##### hud.xml (349 vs 333 lines — 16 added)
The main HUD root. QOLLOCK adds:
- **Script includes:** 6 QOLLOCK JS files (`ql_utils`, `ql_shared_presets`,
  `ql_recent_purchases_data`, `ql_minimap_crate_data`, `ql_perf_overlay`,
  `ql_core`). These are *net-new* — Valve's original has zero scripts at the
  HUD level.
- **Modified `OffscreenEnemySnippet`:** Adds `id="unit_info"`, `id="hero_icon"`,
  `id="health_container"` with `id="health_backer"` and `id="unit_health_bar"`
  sub-panels inside the offscreen indicator. These explicit IDs are required
  because QOLLOCK's JS targets them via `FindChildTraverse`.
- **Modified `OffscreenPingSnippet`:** Same pattern — adds `id="playerPulse"`
  and `id="hero_icon"` so JS can target ping indicators.
- **Risk if Valve changes:** The `OffscreenEnemySnippet` and
  `OffscreenPingSnippet` structures. If Valve adds/removes sub-panels or
  renames classes, QOLLOCK's injected IDs might collide or become orphaned.

##### hud_health_container.xml (95 vs 56 lines — 39 added)
The health bar container. This is QOLLOCK's most transformative change:
- **Minecraft healthbar root:** `MinecraftHeartsRoot` with the entire MC

The core problem: these are **full file copies, not patches**. When Valve
updates any of these 28 files (which happens in ~30% of game patches based
on the mod's update history), one of three things happens:
1. **Silent breakage:** A panel QOLLOCK targets changes ID, and
   `FindChildTraverse` returns null — feature silently stops working but
   doesn't crash (mitigated by `IsPanelValid` guards).
2. **Layout corruption:** A panel hierarchy shifts, and QOLLOCK's wrappers
   place elements in wrong positions — seen as visual bugs.
3. **New Valve features missing:** QOLLOCK's copy lacks panels Valve added
   since the copy was made — new game features don't appear in the modded HUD.

**Status:** Unresolved. The only long-term fix is migrating from full XML
copies to JS panel injection (`$.CreatePanel` + `BLoadLayoutSnippet`) for
QOLLOCK-specific panels, and CSS-only changes for style modifications.
(Identified as Fix 13 in stability proposals.)

**F4. No automated regression testing.** The schema validation script
(`scripts/validate_compact_schema.js`) validates schema integrity but there
are no tests for feature behavior, config round-trips, or panel interactions.
(Identified as Fix 18.)

**Status:** Unresolved. All testing is manual (play test for 3-5 minutes).

### 7.2 High — Performance

**F5. Main loop always evaluates ~40 gate conditions.** When even one feature
is enabled, `ResolveRuntimeGates()` computes every gate. Many of these are
inexpensive (boolean checks), but some like `NeedsEnemyColorWarningRuntimeWork()`
and `NeedsGameplayMouseCursorRuntimeWork()` perform panel validity checks and
class tests.

**Status:** Partially mitigated by `State.allFeaturesDisabled` hard-gate and
the signature-based gate caching, but no per-gate lazy evaluation.

**F6. High-tier features scan every tick.** SPM, unspent, enemy colored health,
and nicknames perform panel tree scans every time they're gated in. These scans
could be spread across more ticks or use event-driven triggers.

**Status:** Partially mitigated by per-feature throttle timers (e.g.,
`enemyColoredHealthPanelCacheNextMs`, `spm.panelCacheNextMs`), but the throttle
is still per-tick — within the throttled window, panels are re-scanned.

**F7. Compass loop at 20Hz is always-on for minimap rotate.** Even when
`MINIMAP_ROTATE_WITH_PLAYER` is off, the compass loop still runs at degraded
intervals to check if it should activate.

**Status:** Mitigated by idle degradation (0.5s idle / 1.0s deep-idle for
compass), but the active-path check overhead remains.

### 7.3 Medium — Code Health

**F8. Dead code accumulation.** The stability audit estimated 5-15% dead code
in `ql_core.js`. Deprecated feature branches behind `false` gates, testing code
left in production, and unreachable branches accumulate over 30+ feature
iterations. (Identified as Fix 4.)

**Status:** Partially addressed. Some deprecated paths have been cleaned, but
the `FORCE_OLD_ENEMY_ULT_INDICATOR_ALWAYS_ON = false` and similar patterns
remain.

**F9. Duplicated normalization between settings and core.** The compact schema
registration must be mirrored in both `ql_settings.js` and `ql_core.js`.
Divergence between the two registries causes import/export round-trip failures.
(Identified in the ADDING_SETTINGS.md as a common mistake.)

**Status:** Unresolved. The two files share `ql_shared_presets.js` for
normalization functions but maintain independent schema registries.

**F10. Magic numbers without documentation.** ~44 named constants with no
rationale comments. The stability audit (Fix 14) identified examples like
`COMPASS_SPEED_SCALE = 2.12`, `UNSECURED_SOULS_RATE_EMA_ALPHA = 0.35`,
`ZIP_BOOST_READY_FLASH_MS = 2000` — all empirically tuned but undocumented.

**Status:** Unresolved. Most constants have descriptive names but no derivation
or tuning notes.

**F11. CSS size (~70 files).** The mod ships many full CSS copies where only
a few values differ. The stability audit (Fix 5) estimated 30-50% CSS reduction
via `@define` variable consolidation.

**Status:** Unresolved.

### 7.4 Low — Maintainability

**F12. Monolithic `ql_core.js` (31,408 lines).** All features live in one file
with ~600 State fields, making it difficult to:
- Find where a specific feature is implemented
- Test features independently
- Review changes to unrelated features
- Parallelize development

(Identified as Fix 12.)

**Status:** Not addressed. The `ql_utils.js` extraction (Fix 10) was the first
step, but the main file remains monolithic.

**F13. Settings UI file is ~33,000 lines.** `ql_settings.js` is similarly
monolithic and too large to read in a single pass. Tab definitions, row creation,
and metadata are all inline.

**Status:** Not addressed.

**F14. No TypeScript/migration path.** The codebase is pure ES5 JavaScript
(no `let`, `const`, arrow functions, template literals) because Panorama's JS
engine (V8, but an older embedded version) doesn't support modern syntax.
There's no transpilation step.

**Status:** Inherent limitation of the Panorama runtime. Could be addressed
with a Babel/SWC build step, but adds pipeline complexity.

### 7.5 Observations — Architecture Strengths

The mod demonstrates several excellent engineering decisions:

1. **Feature OFF = zero work.** The gate system and `allFeaturesDisabled`
   hard-gate ensure that when everything is off, the loop is nearly free.

2. **Error isolation.** `ExecuteFeature()` with auto-disable prevents cascading
   failures — a single broken feature won't crash the entire mod.

3. **Rollback switches.** `CORE_SCHEDULER_V2_ENABLED`, `FEATURE_STAGGER_ENABLED`,
   and `CORE_SCHEDULER_STAGGER_CLEANUP` can all be toggled to revert to simpler
   behavior for debugging.

4. **Schema version discipline.** The semver-tagged compact binary encoding
   with registry-based migration is more sophisticated than any other Deadlock
   mod's config system.

5. **Idle degradation.** The 4-level degradation system (active/idle/deep_idle/
   background) with FPS-aware detection is well-designed.

6. **Utility extraction.** The `ql_utils.js` extraction with graceful fallback
   stubs when not loaded is cleanly implemented.

7. **Throttling everywhere.** Logging, error reporting, panel scanning, and
   source searching all have per-source throttle timers.

8. **Signature-based caching.** Config gates, runtime style states, and panel
   class sets all use string signatures to avoid redundant work.

### 8.1 Panorama: C++ Native HUD, Not JS-Driven

Valve's original panorama files (`_valve_reference/valve_ingame_panorama_readonly/`)
contain only **4 JS files** (322 lines total) — all utility-only. The HUD is
entirely driven by compiled C++ custom panel types:

| Panel Type | File | What It Provides |
|-----------|------|-----------------|
| `CitadelHudHealth` | `hud_health.xml` | Health bar with vertical ProgressBar, shield sub-bars, regen, pending damage/heal |
| `CitadelHudAbilityButton` | `citadel_hud_ability_button.xml` | Cooldown display via `{s:cooldown_sec}` binding, upgrade pips, charge counters |
| `CitadelHudTopBarPlayer` | `citadel_hud_top_bar_player.xml` | Per-player health, souls, KDA, abilities, items, ult status |
| `CitadelHudHeroShop` | `citadel_hud_hero_shop.xml` | Full shop with category nav, search, recent purchases, stats |
| `HudMinimap` | `hud_minimap.xml` | Particle-scene minimap with zipline lanes, player icons, boss markers |
| `CitadelStatusEffect` | `citadel_status_effect.xml` | Status effect icons with cooldown overlays, stack counts |
| `CitadelModsPurchasedPanel` | `citadel_mods_purchased_panel.xml` | Item grid with `show_cooldowns` attribute for CD visualization |

**Validation:** QoL Lock's approach — reading panel attributes, injecting CSS
classes, and manipulating layout — is the correct pattern for modding this
architecture. There is no JS API for health values, cooldown state, or soul
counts. All data must be scraped from panel attributes, text labels, or CSS
classes, which QoL Lock does correctly.

### 8.2 Enemy Health Bars — Dual Overlay Versions

Valve ships **three** unit status overlay versions:
- `unit_status_overlay.xml` (original)
- `unit_status_overlay_v2.xml` (current — with `unit_healthbar_lagging`, `unit_healthbar_delta`, `unit_healthbar_healing`, shield bars, stamina pips)
- `unit_status_overlay_old.xml` (legacy)

QoL Lock's `ENABLE_ENEMY_ULT_OLD` targets the legacy overlay via `FORCE_OLD_ENEMY_ULT_INDICATOR_ALWAYS_ON`,
while `ENABLE_ENEMY_V2_ENHANCED`/`ENABLE_ENEMY_V2_ULT_INDICATOR`/`ENABLE_ENEMY_V2_LEVEL`
use attribute bridge events on the V2 overlay. This dual-path approach is
correct but fragile — Valve could remove the old overlay entirely, breaking
the legacy path.

**Recommendation:** Consider deprecating the old enemy ult indicator path and
consolidating on V2. The `FORCE_OLD_ENEMY_ULT_INDICATOR_ALWAYS_ON = false`
constant is a potential removal candidate.

### 8.3 Reference Mod: Top Bar Plus

The Top Bar Plus mod (`_mods_reference/top_bar_plus/`) confirms standard
Panorama modding patterns that QoL Lock also uses:

| Pattern | Top Bar Plus | QoL Lock |
|---------|-------------|----------|
| Root panel navigation | `findRoot()` + `FindChildTraverse()` | `GetUIRoot()` + `FindChildTraverse()` |
| Game time from dual sources | API + clock text parsing | Same approach |
| CSS class as state indicator | `BHasClass("connectedToHideout")` | `isConnectedToHideout()` via root class |
| UI-scraped game data | Parses `ScoreLabel` text for souls | Parses label text for SPM, unspent, stat bonuses |
| Scheduled loop | `$.Schedule(1, tick)` at 1Hz | `$.Schedule(delay, loop)` at 5-20Hz with degradation |
| Hideout detection | Pauses timers in hideout | Degrades to deep-idle in hideout |
| Clock rollback handling | Detects time-going-backwards | Not implemented in QoL Lock |
| Retry boot | `$.Schedule(0.5, boot)` | `BootstrapUnitTargetStyles()` with retry |

**Gap identified:** QoL Lock does not handle clock rollback (match restart).
Top Bar Plus's `tick()` checks `now + 5 < lastGlobalSec` and `lastGlobalSec > 30 && now <= 2`
to detect this. Adding clock rollback detection would improve robustness
during match restarts and lobby transitions.

### 8.4 Health Bar CSS Patterns

### 9.3 CreateRow Function (lines 19,632–20,969)

The 338-line `CreateRow(parent, label, configId, type, min, max, step, options, description)`
is the single row factory for ALL 244 settings. It:

1. Creates a `SettingRow` panel with type-specific CSS class
2. Creates a `LabelContainer` with localized label
3. Stores config keys as panel attributes for reset discovery
4. Creates a reset-to-default button (refresh icon)
5. Binds changed-state badge (shows when value ≠ default)
6. Binds tooltip with perf impact tier + creator attribution
7. Dispatches to type-specific construction (slider, toggle, dropdown, etc.)

**Type-specific handlers within CreateRow:**

- **slider** (lines 19,770–19,871): Horizontal slider + text entry. Handles opacity (0–1 → 0–100%), float, angle, seconds formatting. Calls `MarkConfigDirty()` (debounced save) on change.
- **runtime_slider** (lines 19,872–19,998): State stored in `gRuntimeSliderState`, runs console commands.
- **multitoggle** (lines 19,999–20,169): Multi-button group or checkbox style. Supports `color-warning`, `bridge-buff-filter`, `item-cooldown-filter` sub-layouts.
- **runtime_buttongroup** (lines 20,170–20,234): Runtime toggle state with optional audio test playback.
- **buttongroup** (lines 20,235–20,323): Segmented button group with language/theme/difficulty specializations.
- **palette** (lines 20,324–20,405): Color swatch picker, groups of 10 per row.
- **dropdown** (lines 20,406–20,686): Custom option rendering with hero icons, language icons, voice type metadata.
- **preset** (lines 20,687–20,707): Limited — most preset UI is via `CreatePresetGrid`.
- **actionbutton** (lines 20,708–20,870): Command-executing button with optional on-death checkbox for arcade games.
- **runtime_toggle** (lines 20,871–20,906): Console command toggle.
- **toggle** (lines 20,907–20,964): Default type. Switch with `ToggleActive`/`ToggleOn`/`ToggleOff` classes.

### 9.4 Config I/O & Auto-Save

**Read:** `SyncConfigFromStorage()` (line 13,166) reads from panel attributes on
three targets (panel, root, Hud), selects the highest-revision entry, parses the
JSON envelope, normalizes through the migration chain, and assigns to `MOD_CONFIG`.

**Write:** `SaveAndSync()` (line 13,314) is the canonical save. It:
1. Normalizes `MOD_CONFIG`
2. Wraps via `WrapConfigForStorage(config)` → `{"schema":"3.1.4","data":{...}}`
3. Skips if unchanged from `gLastSavedConfigRaw`
4. Writes to all three panel targets with incrementing revision
5. Persists to `$.persistentStorage` as fallback
6. Publishes palette color bridge attributes
7. Refreshes theme classes and preset highlights

**Auto-save:** Every user interaction mutates `MOD_CONFIG` in-place and triggers either:
- `MarkConfigDirty()` — debounced by 300ms (used for sliders)
- `SaveAndSync()` — immediate (used for toggles, dropdowns, buttons)
- `FlushPendingSave()` — forces immediate flush before imports/resets

**Revision tracking:** `QOL_USER_EDIT_REV` attribute stores monotonically
increasing integer. On write: `max(panel_rev, root_rev, hud_rev) + 1`.
On read: highest-revision source wins, priority hud > root > panel for ties.

### 9.5 Schema Registry (51 Versions)

The compact schema chain in `ql_settings.js` is **structurally identical** to
the build payload schema in `ql_core.js`, but maintained independently:

| Aspect | ql_settings.js | ql_core.js |
|--------|---------------|------------|
| Base schema | `COMPACT_SCHEMA_V2` (69 fields) | `BUILD_CATEGORY_COMPACT_SCHEMA_V2` (69 fields) |
| Version chain | V2 → V60, then 2.0.0 → 3.1.4 | Same structure, different constant names |
| Helper functions | `AppendUniqueSchemaFields`, `CloneSchemaWithFieldOverrides`, `CloneSchemaWithoutFields` | Same logic, `Payload`-prefixed names |
| Registry | `COMPACT_SCHEMA_REGISTRY` (51 entries) | `BUILD_CATEGORY_COMPACT_SCHEMA_REGISTRY` |
| Latest schema | `COMPACT_SCHEMA_3_1_4` (1 new field: `UNIT_TARGET_HINT_SIZE`) | Same |

**51 registered schema versions** from `2.0.0` (wire version 1) through `3.1.4`
(wire version 2). All versions except `2.0.0` use wire version 2. This means
the only meaningful wire-version migration was the 2.0.0 → 2.0.1 transition
— all 50 subsequent versions are schema-field additions within wire version 2.

**27 of the 51 versions have NO comments** explaining what changed between them.
The version gaps (e.g., 2.2.7 → 2.2.10, 2.3.3 → 2.3.7 being aliases) suggest
internal snapshots or skipped versions during development.

### 9.6 Export/Import System

**Export:**
```
GetCurrentExportSettingsString()
  → SerializeCompactV2(MOD_CONFIG)
    → QOL_CODEC.SerializeCompactBinary(config, schema, wireVersion, resolver)
      → bit-packed binary string (version byte + field bits + checksum)
    → ToBase64Url(binary)
  → "[QOL-3-1-4]:" + base64
```

**Import:** `TryApplyImportStringWithDiagnostics(raw)` parses the `[QOL-X-Y-Z]:`
prefix, extracts the semver, decodes base64, deserializes via the appropriate
schema version, builds a candidate config clamped to schema bounds, runs the
full normalization chain, and preserves UI-only settings (`DRAG_ENABLED`,
`PREVIEWS_ENABLED`).

**Diagnostics reported:** `appliedKeys`, `unknownKeys`, `clampedKeys` — the
UI shows these to help users understand import results.

### 9.7 Search System

The search index is built by running every tab's content renderer in a
**collect-only mode** (`gSearchCollectMode = true`) where `CreateRow` records
rows into an index instead of creating UI panels. The index is cached per
language and rebuilt on language change.

Search matching (`IsSearchRowMatch`) checks: label text, subInfo (secondary label),
configId, section title, tab title, and aliases. All normalized to lowercase.

Results are rendered with CSS animation classes and grouped by tab/section.

### 9.8 Preview System

`PREVIEWS_ENABLED` controls real-time visual previews. When enabled, every
slider change triggers `ShowConfigPreviewForConfigId()` which dispatches to
feature-specific preview functions:
- `ShowMinimapSizePreview()` — adjusts a preview circle
- `ShowCompassPreview()` — positions a compass overlay
- `ShowZipBoostPreview()` / `ShowUnsecuredSoulsPreview()` / etc.
- `ShowKeyboardOverlayPreview()` / `ShowItemCooldownPreview()` / etc.

Each preview function guards on `PREVIEWS_ENABLED === 1` and reads relevant
MOD_CONFIG values to position/style a preview panel in real-time.

### 9.9 Translation Infrastructure

**12 languages** supported via 11 translation maps (English is the source language,
no translation needed). Each map contains ~700 key-value pairs, totaling ~8,000
lines of translation data inline in the file.

The `LocalizeSettingsText(text, force)` function looks up the English text in
the appropriate language map and returns the translation. Falls back to the
original English text if no translation exists.

**Issues found:**
- 4 language-specific normalization functions are **empty pass-throughs**
  (`NormalizeFrenchSettingsText`, `NormalizePortugueseSettingsText`,
  `NormalizeBrazilianPortugueseSettingsText`, `NormalizeSpanishSettingsText`)
  — they are called but do nothing.
- `gMissingRuSettingsStrings` tracking map is populated but never read or reported.
- Translation maps are independent objects with no shared default — each must
  duplicate the same ~700 key names.

### 9.10 Dead Code & Duplication

**Dead code identified:**
- `SettingsRuntimeLog(msg)` — always an empty no-op (`SETTINGS_RUNTIME_LOG = false`)
- `SETTINGS_SAVE_DISABLED_WARNING` and `SETTINGS_SAVE_HOVER_WARNING` — defined but never referenced
- `SETTINGS_SAVE_LOADER_ENABLED = true` — never checked
- 4 empty translation normalization functions
- `gMissingRuSettingsStrings` — populated but never reported

**Duplication identified:**
- **Schema definitions duplicated between ql_settings.js and ql_core.js:**
  Both files maintain independent 60-version schema chains with 95% identical
  field definitions. Only function names differ (e.g., `AppendUniqueSchemaFields`
  vs `AppendUniquePayloadSchemaFields`).
- **BHOP UI row duplicated** at two locations within the MOG tab handler
  (search-collect mode line 22,741 and normal render line 22,789).
- **UI Controls section duplicated** between HUD tab (line 22,107) and UI tab
  (line 22,218) — ~9 identical `CreateRow` calls for the same config keys.
- **Config tab general rows duplicated** between search-collect mode
  (lines 14,222–14,228) and normal mode (lines 14,246–14,252).
- **Description overrides duplicated** between HUD and UI category sections in
  `SETTING_DESCRIPTION_OVERRIDE_BY_CATEGORY_ROW` — identical descriptions with
  different category prefixes.
- **The Size/Opacity/Offset slider pattern** repeated 22+ times across 10 sections —
  80 slider rows that vary only in configId, label, and min/max bounds.
  All could be generated from a data table.

**Data error:** `ENABLE_COLORED_HEALTHBAR` appears in both `COMPACT_SCHEMA_V2`
(base, line 11,349) and `COMPACT_SCHEMA_V24` (extension, line 11,452), creating
a harmless-but-wasteful duplicate in every subsequent schema version.

**Metadata completeness:**
- `SETTING_CREATED_BY_BY_CONFIG`: ~77 entries, missing ~160 newer config keys
- `SETTING_CREATED_BY_BY_LABEL` and `SECTION_CREATED_BY_BY_TITLE`: empty objects
- `SETTING_PERF_IMPACT_TIERS`: ~220 entries, missing ~30-40 config keys
- `SETTING_DESCRIPTION_OVERRIDE_BY_CONFIG`: ~133 entries, missing ~70 recent additions
